## Context

On 2026-09-10 the AID operator received a return-to-work task: put the classifier into production on an EasyPanel instance already created for the team (panel title **Easypanel Aid-Lab**, panel URL `https://191.234.171.158/`). Panel login is the Bitwarden item **Easypanel Aid - Lab**. The briefing names the product "ementário"; in this repository that work is the Django app **classificador-receita**.

The app today is a local developer setup. `README.md` lists Docker among the technologies, but the tree has no `Dockerfile`. `classificador/settings.py` ships `DEBUG = True`, an insecure hardcoded `SECRET_KEY`, `ALLOWED_HOSTS = []`, and a PostgreSQL profile fixed to `localhost` / `postgres` / `postgres`, with SQLite only when `USE_SQLITE=1`. There is no production process (the dev task is `runserver`) and no `STATIC_ROOT`.

The panel URL is the control plane. Day-to-day maintainers need a different link: the Django site, where they sign in and edit the classifier. They should not need EasyPanel admin for that work.

Local tracking: parent issue `#77` (`_dev/gh/issues/0077_EPIC-01-Publicar-o-classificador-no-servidor-da-secretaria.yml`). mid-01 through mid-07 own `#78`–`#84`. mid-00 has no issue.

## Objective

When this plan is done, a conventional AID teammate can open one HTTPS link, sign in to Django, and maintain the revenue classifier on the secretariat Aid-Lab server. Deploy operators use EasyPanel to keep that service running. Secrets stay in Bitwarden, not in the repository.

### mid-01 — Inventory Aid-Lab on EasyPanel

**Context:** The panel exists, but this repo does not record what is already configured on it. Deploy steps that assume an empty project will fail if a project, domain, or database is already there.
**Objective:** A short inventory the operator can trust before any service is created.
**Issue(s):** `#78`
**Scope:**
  `In scope:` Sign in to EasyPanel Aid-Lab with the Bitwarden item. Record projects, services, domains, whether GitHub (or another Git remote) is connected, and whether PostgreSQL is already provisioned. Record the hostname pattern EasyPanel will give the app.
  `Out of scope:` Creating or deleting services. Copying passwords, tokens, or screenshots of secrets into Git.
**Acceptance criteria:**
  - [ ] Inventory names the EasyPanel project to use (new or existing) and any service already bound to this app.
  - [ ] Inventory states how the app will be deployed (Git repository connected to the panel, or an image built elsewhere).
  - [ ] Inventory proposes the public app hostname and confirms it is distinct from the panel URL `https://191.234.171.158/`.
  - [ ] No secret from Bitwarden or the panel appears in the inventory file.

### mid-02 — Environment-based Django settings

**Context:** A container on EasyPanel cannot use `DEBUG=True`, an empty `ALLOWED_HOSTS`, or a database host fixed to `localhost`.
**Objective:** One settings path for local work and one for the lab, selected by environment variables.
**Issue(s):** `#79`
**Scope:**
  `In scope:` Read `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, and PostgreSQL connection fields from the environment. Keep `USE_SQLITE=1` as the local switch documented in `.env.example`. Document every variable the lab service needs, with placeholders only.
  `Out of scope:` New classifier features. Changing seed contents. Putting real lab passwords in `.env.example` or in settings.
**Acceptance criteria:**
  - [ ] With `USE_SQLITE=1` and no new variables, `poetry run task migrate` and `poetry run task dev-server` still behave as in the README.
  - [ ] With lab variables set, Django accepts the inventory hostname, talks to a non-local PostgreSQL, and does not use the hardcoded insecure `SECRET_KEY`.
  - [ ] `.env.example` lists the lab variables and states that real values belong in EasyPanel and Bitwarden.

### mid-03 — Container image

**Context:** EasyPanel runs services from images. The repository has Poetry, Python `>=3.12`, and no image definition.
**Objective:** A Dockerfile that builds the app and serves it as a production process behind the panel proxy.
**Issue(s):** `#80`
**Scope:**
  `In scope:` `Dockerfile`, `.dockerignore`, a WSGI server (Gunicorn or the server the inventory chooses), `collectstatic`, and a start command that migrates then serves. The image must not run `manage.py runserver`.
  `Out of scope:` Publishing the image to a public registry. Loading seeds on every container start. Shipping the Zensical docs site in the same image.
**Acceptance criteria:**
  - [ ] `docker build` succeeds from a clean tree.
  - [ ] The container listens on the port EasyPanel will proxy, and `GET /admin/login/` returns the Django login page when a database is reachable.
  - [ ] Restarting the container does not drop or reload database data.
  - [ ] The image does not copy `.env` or other secret files.

---

### mid-04 — PostgreSQL service

**Context:** The classifier is specified as a PostgreSQL database. SQLite is a local beta switch and is not the shared lab store.
**Objective:** A PostgreSQL service on EasyPanel whose data volume survives app redeploys.
**Issue(s):** `#81`
**Scope:**
  `In scope:` Create or adopt one database service in the Aid-Lab project. Create a dedicated database and user for this app. Point mid-02 variables at that service over the panel's internal network.
  `Out of scope:` Reusing the README defaults `postgres` / `postgres` as the lab password. Opening PostgreSQL to the public internet. Importing SISOR.
**Acceptance criteria:**
  - [ ] The database service stays up after the app container is redeployed.
  - [ ] Django migrates against that database using credentials that are not the repository defaults and are not committed.
  - [ ] The database port is not published on the public host except through EasyPanel's internal network.

### mid-05 — EasyPanel app service and hostname

**Context:** Maintainers need a stable HTTPS link. The panel address is not that link.
**Objective:** An app service on Aid-Lab that builds or pulls mid-03 and is reachable at the hostname from mid-01.
**Issue(s):** `#82`
**Scope:**
  `In scope:` App service, environment from mid-02, domain and TLS as EasyPanel provides them on this host, proxy to the container port, and a health check on a Django URL.
  `Out of scope:` A custom domain outside what the lab host can serve. Production hardening beyond the lab (rate limits, SSO, WAF).
**Acceptance criteria:**
  - [ ] An unauthenticated browser opening the app URL over HTTPS receives a Django response, not the EasyPanel login page.
  - [ ] `DEBUG` is off on that service.
  - [ ] Redeploying from the chosen Git branch or image updates the running app without a manual shell on the host.

---

### mid-06 — First data load and maintainer accounts

**Context:** An empty migrated database does not let anyone maintain the classifier. Seeds today load through `poetry run task carregar`, and staff users through `createsuperuser`.
**Objective:** The lab database holds the initial classifier data and at least one Django staff account for AID.
**Issue(s):** `#83`
**Scope:**
  `In scope:` One controlled seed load (`carregar`) after the first successful migrate. One or more Django staff users for maintainers. Store those passwords in Bitwarden, in an item separate from the panel login.
  `Out of scope:` Automatic seed reload on every deploy. Sharing one personal password in chat or in the repo. Editing classifier business rules.
**Acceptance criteria:**
  - [ ] A staff user can sign in at `<app-url>/admin/` and open the classifier maintenance screens.
  - [ ] Seed data is present after the one-shot load, and a later redeploy does not clear it.
  - [ ] Staff passwords exist only in Bitwarden (or EasyPanel secrets), not in Git.

---

### mid-07 — Handoff to a conventional AID user

**Context:** The product of this epic is access for the team, not only a working panel for the person who deployed it.
**Objective:** A teammate who does not administer EasyPanel can maintain the classifier with the published link.
**Issue(s):** `#84`
**Scope:**
  `In scope:` A runbook under `docs/instalacao/` with the app URL, the login path, the Bitwarden item names (panel vs Django), and who to ask for an account. A check that one other AID person completes login.
  `Out of scope:` Training on classifier business rules. Granting EasyPanel admin to every maintainer.
**Acceptance criteria:**
  - [ ] The runbook URL, opened in a browser without EasyPanel credentials, shows the Django login page.
  - [ ] An AID teammate who is not the deploy operator signs in with their own Django user and reaches a maintenance screen.
  - [ ] The runbook does not contain passwords.

## General acceptance criteria

Epic deliverables:

- [ ] An AID maintainer can open the published HTTPS URL, sign in to Django, and maintain classifier data without using the EasyPanel UI
- [ ] The repository contains a container image definition and the EasyPanel layout is described in the runbook (app service + PostgreSQL)
- [ ] `docs/instalacao/` states the maintainer URL, the Django login path, and the Bitwarden item names
- [ ] Local `USE_SQLITE=1` development still follows the README; the lab service reads host, secret, debug, and database settings from the environment
- [ ] The deployed service rejects the insecure in-repo `SECRET_KEY` and runs with `DEBUG` off
- [ ] No panel, database, or Django password is committed
- [ ] Help or operator docs updated for user-facing **Add** / **Change** items
- [ ] CHANGELOG + manifest bump when this epic delivers a publishable release
